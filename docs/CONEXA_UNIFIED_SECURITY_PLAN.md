# CONEXA RMX — Unified Security & Architecture Plan

## Purpose

This document records the consolidation baseline for `Conxa.rmk` and `Conexa-RMX-DEV`.
The integration branch must preserve the strongest functional and security properties from both repositories without performing a blind merge.

## Integration baseline

- Target repository: `Conexa-RMX-DEV`
- Integration branch: `integration/conexa-unified`
- Functional baseline: `fix/job-state-machine`
- Security hardening source: `Conxa.rmk/main` plus reviewed changes from `fix/firebase-static-config`
- Production `main` is not modified during consolidation.

## Non-negotiable security rules

1. Firebase ID tokens are the identity source for normal application authentication.
2. `ADMIN` / `SUPER_ADMIN` privileges must never be granted by a generic `x-admin-key` or `x-radar-secret` request header.
3. S2S secrets are only for explicitly scoped infrastructure/webhook operations and must use timing-safe comparison.
4. Commercial mutations must be server-authoritative: quote submission, quote acceptance, job state transitions, payment state changes, reviews and verification decisions.
5. Firestore rules use whitelists for client-controlled fields; sensitive commercial fields are backend-only.
6. Transactions are backend-written and treated as an auditable financial ledger; direct client writes are disabled.
7. Public user profiles contain only public data. Private phone/address/document data stays under `users/{uid}/private/info` or another explicitly private structure.
8. Custom claims, if used, are server-managed only. No client endpoint may self-escalate role/privilege.
9. Audit logs are generated by trusted backend operations, not by client-submitted claims of administrative actions.
10. Payment webhooks are verified and reconciled server-to-server; browser redirects are never proof of payment.

## Target commercial state model

### Request / Job lifecycle

`REQUEST_CREATED -> QUOTES_RECEIVED -> PROFESSIONAL_SELECTED -> IN_PROGRESS -> COMPLETED -> REVIEW_PENDING -> CLOSED`

Alternative terminal path: `CANCELLED` where business rules permit it.

### Financial lifecycle

`CREATED -> PAYMENT_PENDING -> PAID -> SERVICE_COMPLETED -> SETTLED`

Alternative paths include `CANCELLED`, `REFUNDED`, and `CHARGEBACK` according to provider events and business rules.

The financial state and service/job state are related but must not be conflated.

## Known implementation gaps to close

- Add an authoritative `startJob` operation.
- Change `completeJob` from `PROFESSIONAL_SELECTED -> REVIEW_PENDING` to the validated `IN_PROGRESS -> COMPLETED` transition, followed by review eligibility.
- Move review creation and professional aggregate updates to a backend transaction.
- Restrict service request updates with an explicit whitelist.
- Disable direct client writes to transactions.
- Validate message authorship against conversation membership.
- Move sensitive verification approval and other administrative mutations behind backend authorization/audit.
- Review `beta_config` and `invite_codes` read permissions.
- Verify the complete custom-claims lifecycle before any production deployment.
- Add tenant/business context consistently before enabling SaaS cross-tenant operations.

## Definition of done for consolidation

The unified branch is not production-ready until:

- TypeScript/build checks pass.
- Core flow tests pass: request -> quote -> accept -> pay -> start -> complete -> review.
- Invalid state transitions are rejected server-side.
- Firestore rules deny direct writes to protected commercial records.
- Tenant/resource ownership is enforced on every sensitive endpoint.
- Admin privileges cannot be obtained through user-controlled request headers.
- Mercado Pago webhook processing is idempotent and authoritative.
- No production/demo fixture data can leak into real Firestore data paths.
- Secrets and private user data are not returned to the browser or AI services unnecessarily.
